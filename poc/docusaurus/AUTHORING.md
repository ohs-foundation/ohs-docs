# OHS PoC Markdown authoring

The public documentation content lives in `docs/`. Authors write normal Markdown and YAML frontmatter; do not edit the site shell, React components, or CSS to update a page.

## Add a setup guide

Create `docs/setups/<guide-name>.md`. The sidebar is autogenerated, so `sidebar_position` determines its order.

```md
---
id: example-guide
title: Example guide
description: One-sentence description shown in the guide header.
slug: /setups/example-guide/
sidebar_position: 2
guide_type: Setup guide
guide_status: Guidance available
guide_focus: What the setup helps an implementer do
repository: client-app
---

## Context

Write normal Markdown here.
```

The shared shell renders the title, description, source link, status, focus, sidebar, and on-page table of contents. Every `##` heading becomes an on-page navigation entry. `repository` must be an identifier in `src/data/playerRepositories.js`; that maintainer map owns the canonical repository name, URL, role, and dependency metadata.

## Use normal Markdown

Use headings, lists, tables, links, fenced code blocks, and Docusaurus admonitions. No JSX import or HTML is required.

```md
:::note
Reference Infrastructure setup material is not yet published. Link to the repository instead of adding an unverified command.
:::
```

## Use reader-facing guide metadata

`guide_type` identifies the page's purpose. Use one of:

- `Quick start`
- `Setup guide`
- `Advanced setup`
- `Setup pending`
- `Concept`

`guide_status` communicates whether the reader can act on the page. Use one of:

- `Guidance available`
- `Setup procedure pending`
- `Setup material pending`

Use `Guidance available` for a page with instructions a reader can follow. Use `Setup procedure pending` when the required deployment procedure has not been published. Use `Setup material pending` when a repository describes a future setup but lacks the files required to run it.

The shared shell communicates this state. Explain its practical impact in the page body without adding process terminology or warnings.

## Use the guide section contract

Where source material permits it, use this order:

1. Context or scope.
2. Prerequisites.
3. Steps.
4. Expected result or checkpoint.
5. Troubleshooting, only when source-backed guidance exists.
6. Next step.

Do not add empty sections or invent checks to make every guide look identical.

## Landing content

`docs/landing.md` owns all landing-page text and section order. Its small amount of frontmatter supplies the hero eyebrow and actions; the rest is ordinary Markdown. Update `LandingPage.jsx` only when changing the shared landing template, not its content.

## Verify an edit

Run the Node 24.18.0 commands from the project completion report:

```sh
npm --prefix poc run build -- --candidate=docusaurus
```

Then run the smoke and accessibility checks listed there. The smoke test asserts that key Markdown text is present in the built page, guarding against a shared shell that drops document content.
