# Authoring OHS docs

Content lives in `docs-content/` as ordinary Markdown with YAML frontmatter. Do not edit
the site shell, React components, or CSS to change a page — the shells render titles,
descriptions, source links, status, focus, sidebar, and the on-page table of contents from
frontmatter alone.

## Add a page

Create the Markdown file under the component directory it belongs to. The sidebar is
autogenerated, so `sidebar_position` determines ordering within a directory and
`_category_.json` names and orders the directory itself.

```md
---
title: Example guide
description: One-sentence description shown under the title.
slug: /ohs-player/setups/example-guide/
sidebar_position: 2
guide_type: Setup guide
guide_status: Guidance available
guide_focus: What the setup helps an implementer do
repository: client-app
---

## Context

Write normal Markdown here.
```

Then add the matching entry to `scripts/routes.json`, whose `title` and `content` must
equal the page's `title` and `description`. `npm run check` fails if they drift, if a page
is missing from the contract, or if the contract references a page that no longer exists.

Every `##` heading becomes an on-page navigation entry. Do not add a body `#` heading: the
shell renders `title` as the page's only `<h1>`.

`repository` must be a key in `src/data/repositories.js`, which owns the canonical
repository label and URL. Add a key there before referencing it.

## Use normal Markdown

Headings, lists, tables, links, fenced code blocks, and Docusaurus admonitions all work.
No JSX import or raw HTML is required.

```md
:::note
Reference Infrastructure setup material is not yet published. Link to the repository
instead of adding an unverified command.
:::
```

## Reader-facing metadata

`guide_type` identifies the page's purpose:

- `Overview` — the entry point for a component or toolkit.
- `Component` — what a component provides and where its reference material lives.
- `Quick start`, `Setup guide`, `Advanced setup` — instructions a reader follows.
- `Concept` — relationships and decisions rather than steps.
- `Community` — contribution and process guidance.

`guide_status` tells the reader whether the page can be acted on today:

- `Guidance available` — instructions a reader can follow now.
- `Reference pending` — the component is real but its guides are not yet in this site.
- `Setup procedure pending` — the deployment procedure has not been published.
- `Setup material pending` — a repository describes a future setup but lacks the files
  required to run it.

The shell communicates this state. Explain its practical impact in the page body without
repeating the label or adding process terminology.

## Guide section contract

Where the source material supports it, use this order:

1. Context or scope.
2. Prerequisites.
3. Steps.
4. Expected result or checkpoint.
5. Troubleshooting, only where source-backed guidance exists.
6. Next step.

Do not add empty sections or invent checks to make every page look identical.

## Landing page

`docs-content/index.md` owns the landing page's text and section order. Its frontmatter
supplies the hero eyebrow and the two calls to action; everything else is ordinary
Markdown. Edit `src/components/ohs/LandingPage.jsx` only to change the shared template,
never its content.

## Verify an edit

```sh
npm run build
npm run check
```

The build fails on any broken internal link or broken Markdown link. The check verifies
the route contract, the frontmatter contract, and that each built page still contains its
own title and description text — guarding against a shell change that silently drops
document content.
